# ПерсДанные

Премиальный тёмный B2B-лендинг сканера соответствия сайтов 152-ФЗ / РКН.

## Запуск на Windows

```bat
cd /d D:\persdannye
copy .env.example .env.local
npm install
npm run dev
```

Откройте http://localhost:3000

Сборка: `npm run build`

## Переменные окружения

См. `.env.example`:

- `PARSER_API_BASE` — публичный URL парсера. **Если не задан, сайт работает на отполированном mock.**
- `PARSER_API_EMAIL` + `PARSER_API_PASSWORD` — JWT через `POST {BASE}/api/auth/login`
- или `PARSER_API_TOKEN` — Bearer, если пользователей в БД ещё нет
- `TELEGRAM_BOT_TOKEN` + `TELEGRAM_CHAT_ID` — мгновенные алерты менеджеру
- `ALLOWED_ORIGINS` — точные Origin для `POST /api/leads` через запятую (прод и preview Vercel). Нет заголовка, `null` и чужой хост — 403
- `PD_BFF_SIGNING_SECRET` — ключ HMAC для `X-PD-Sig` на каждом запросе BFF в парсер. `ts` — unix-секунды (`Math.floor(Date.now() / 1000)`), снимаются прямо перед каждым fetch и не кэшируются: парсер принимает подпись в окне ±60 с. Строка подписи: `ts`, `METHOD`, `pathname`, `ip`, `sha256 hex` сырого тела, через перевод строки. METHOD заглавными, кодировка hex окончательная. path — pathname того URL, который уходит в fetch (`/public/lead`, не `/api/leads`). Префикс базы входит в подпись: `PARSER_API_BASE=https://host/api` подписывается как `/api/public/lead`. Без query, fragment и завершающего `/` (`/public/lead/` и `/public/lead?x=1` подписываются как `/public/lead`). Хэш — SHA-256 тех байт, которые уходят в fetch; без тела берётся sha256 пустой строки. Эталон, ключ `test-key-0123456789abcdef0123456789abcdef`, `ts` `1700000000`, `POST` `/public/lead`, ip `203.0.113.10`: пустое тело — `7e6b604153f10ada26d35f39a4b91cf2b16a5ceb55a0c9745f214e8f7b69e98a`; тело `{"name":"Test"}` (15 байт) — `1810e470f8492479571d2a4b9d324cf2e6a821bf2767390680925d048a40f0c9`. Секрет не короче 32 байт. `PD_BFF_SIGNING_SECRET_PREV` необязателен, те же 32 байта, короче игнорируется: BFF подписывает текущим ключом, парсер на время ротации может принимать любой из двух. В проде пустой или короткий текущий секрет не пускает запрос в парсер: ответ 503 без подробностей. Вне прода такие заголовки просто не ставятся. Заголовки Vercel (`x-vercel-forwarded-for`, затем `x-real-ip`) читаются только при `VERCEL=1`. Берётся первый адрес, trim, без порта и zone id, и он должен проходить `net.isIP`. Оба заголовка невалидны — 503, парсер не вызывается. Клиентские `x-real-ip` и `x-forwarded-for` подписанный адрес не заменяют; `x-forwarded-for` не читается. Vercel перезаписывает входящий `X-Forwarded-For` и ставит `x-real-ip` тем же адресом. `x-vercel-forwarded-for` остаётся, даже если прокси перед Vercel подменил `X-Forwarded-For`. Если `VERCEL` не `1` и `PD_DEPLOY_ENV` не `prod`, подписывается фиксированный `192.0.2.1`. При `PD_DEPLOY_ENV=prod` без `VERCEL=1` этот адрес не подписывается: ответ 503, парсер не вызывается
- Заявка уходит один раз на `POST {BASE}/public/lead` (старый `/api/leads` парсера удалён и отвечает 404). Без bearer и без `smart_token`. Браузер передаёт `Idempotency-Key` (UUID), который меняется вместе с телом заявки; тот же ключ только если тело не изменилось. BFF всегда его пересылает, парсер пока этот заголовок игнорирует. Повтор ключа — при ручной отправке того же тела и при одном автоповторе. Браузер сам не повторяет. BFF один раз повторяет **503** с `Retry-After`, если после ожидания остаётся 30 с на вторую попытку и ещё 5 с до лимита обработчика 60 с. `Retry-After: 30` не влезает. Обрыв и таймаут — 503 без подробностей. Иначе повтор такой: новый `ts`, новая подпись, те же байты тела и тот же `Idempotency-Key`. **401**, **413** и **429** не повторяются. Если ожидание не влезает, клиент получает 503 без подробностей парсера. Тело исходящей заявки больше 16384 байт — свой **413**, парсер не вызывается и запрос не подписывается. Любой ответ 503 на форме показывает «Не удалось отправить заявку, попробуйте через несколько минут»; если в ответе есть `Retry-After` (секунды или HTTP-date), текст становится «попробуйте через ~N мин». Недоступный Redis — 503 `rate_limit_unavailable` и `Retry-After: 30`: ожидание не влезает, BFF второй раз не шлёт. На форме «через ~1 мин». Введённые поля остаются
- Если токен или chat id не заданы, алерт пропускается с записью в лог (сайт не падает)
- `NEXT_PUBLIC_SHOW_FINES=true` — вместе с `approved: true` в `content/fines.ts` показывает таблицу штрафов и калькулятор. Пока юрист не поставил `approved: true`, даже с флагом цифр нет. Без флага блок скрыт целиком.
- `PD_COLLECTION_ENABLED=true` — серверная переменная без `NEXT_PUBLIC_`. Сбор заявок, проверки URL, Метрики и необязательных cookie включается только вместе с опубликованной политикой (`show_site_legal`) и redeploy. Иначе сбор выключен.

Токены **не** отдаются в браузер — только серверный BFF.

## Как работают алерты

Когда заданы `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`, BFF пишет менеджеру в Telegram:

1. **Любая проверка URL завершилась** (`phase === done`, с рисками и без) — «Новый клиент с лендинга»:
   - сразу после опроса статуса (`GET /api/checks/{id}`)
   - текст: домен, ссылка, риски да/нет, находки, контакты если есть
   - PDF `sendDocument` только если есть риски и `pdf_ready`
2. **Новая заявка** (`POST /api/leads`) — отдельное сообщение «Новый клиент с лендинга» с полями формы и призывом взять в работу

Без Telegram-переменных сайт работает как обычно, алерты просто не уходят.

## Деплой

В Production env Vercel (`VERCEL_ENV=production`):

- Не задавайте `E2E`, `SUPPRESSION_MOCK`, `OUTBOUND_MOCK`, если `VERCEL_ENV=production` или `PD_DEPLOY_ENV=prod`. Непустое значение останавливает такую сборку. `NODE_ENV` не проверяется: локальная сборка и CI без этих флагов проходят, в том числе при `E2E=1`.
- `ALLOWED_ORIGINS` и `PD_BFF_SIGNING_SECRET` обязательны. Секрет короче 32 байт останавливает такую сборку так же, как тестовая переменная.

На превью эти три переменные можно оставить. В Production их переносить нельзя. На VPS задаётся `PD_DEPLOY_ENV=prod`.

## Parser BFF

Браузер вызывает только:

- `POST /api/checks` `{ "url", "lead?" }` — создать проверку. Если в `lead` есть имя, email или телефон, без `consent: true` BFF отвечает 400 и проверку не создаёт. При согласии парсеру уходит `{ url, mode: "quick" }` и `lead` (`consent: true`, `consent_text_version`, source `landing`). Старый парсер, который отвергает лишние поля, получает повтор с `{ url }`
- `GET /api/checks/[id]` — статус / находки (poll 1,5 с, пока проверка идёт)
- `GET /api/checks/[id]/pdf` — прокси PDF с авторизацией на сервере
- `POST /api/leads` — заявка с обязательным согласием

Если `PARSER_API_BASE` задан, BFF логинится в парсер, создаёт скан и маппит фазы `queued | open | extract | rules | pdf` (+ `done | error | blocked`).

Для **ngrok free** (`*.ngrok-free.dev`) BFF на каждом серверном запросе к парсеру ставит заголовок `ngrok-skip-browser-warning: true` и `User-Agent: PersDannye-BFF/1.0`, чтобы не упираться в interstitial. Токены по-прежнему только на сервере.

## Что есть на сайте

- `/` — лендинг с проверкой URL, FAQ, формой заявки
- `/check` — отдельная страница проверки
- `/privacy`, `/cookies`, `/terms` — юридические страницы
- Cookie-баннер с категориями; аналитика только после согласия
- Согласие на ПДн в форме заявки и в блоке «Контакты для менеджера» (обязательный чекбокс, по умолчанию снят)
- Заявки принимаются только `POST /api/leads`. Страницы и API со списком заявок нет

Реквизиты оператора: `lib/company.ts`.

## CI / npm audit

CI блокирует два аудита.

1. `npm audit --omit=dev --audit-level=high` — зависимости прод-сборки, без исключений.
2. Полный `npm audit --json` разбирает `scripts/audit-allowlist.mjs`. Любой high или critical роняет job.

Единственное исключение — [GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm) (`braces`). Оно действует только если все пути к пакету идут через `eslint-config-next`: это dev-дерево ESLint, опубликованного исправления нет. `eslint-config-next` не понижаем.
