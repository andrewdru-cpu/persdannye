# ПерсДанные

Премиальный тёмный B2B-лендинг сканера соответствия сайтов 152-ФЗ / РКН.

## Запуск на Windows

```bat
cd /d D:\persdannye
copy .env.example .env.local
npm install
npm run dev
```

Откройте http://localhost:3000

Сборка: `npm run build`

## Переменные окружения

См. `.env.example`:

- `PARSER_API_BASE` — публичный URL парсера. **Если не задан, сайт работает на отполированном mock.**
- `PARSER_API_EMAIL` + `PARSER_API_PASSWORD` — JWT через `POST {BASE}/api/auth/login`
- или `PARSER_API_TOKEN` — Bearer, если пользователей в БД ещё нет
- `TELEGRAM_BOT_TOKEN` + `TELEGRAM_CHAT_ID` — мгновенные алерты менеджеру
- `ALLOWED_ORIGINS` — точные Origin для `POST /api/leads` через запятую (прод и preview Vercel). Нет заголовка, `null` и чужой хост — 403
- `PD_BFF_SIGNING_SECRET` — ключ HMAC для `X-PD-Sig` на каждом запросе BFF в парсер. `ts` — unix-секунды (`Math.floor(Date.now() / 1000)`), снимаются прямо перед каждым fetch и не кэшируются: парсер принимает подпись в окне ±60 с. Строка подписи: `<ts>.<METHOD>.<pathname>.<ip>`, METHOD заглавными, кодировка hex окончательная. path — путь запроса в парсер (`/public/lead`, не `/api/leads`), без query, fragment и завершающего `/` (`/public/lead/` и `/public/lead?x=1` подписываются как `/public/lead`). Эталон: ключ `test-key-0123456789abcdef0123456789abcdef`, сообщение `1700000000.POST./public/lead.203.0.113.10`, подпись `83228275db043cb69f487006351f672bf3b33d131672a33a9ecd8e865e9e102f`. Секрет не короче 32 байт. В проде пустой или короткий секрет не пускает запрос в парсер: ответ 503 без подробностей. Вне прода такие заголовки просто не ставятся
- Заявка уходит один раз на `POST {BASE}/public/lead` (старый `/api/leads` парсера удалён и отвечает 404). Без bearer и без `smart_token`. Браузер передаёт один `Idempotency-Key` (UUID); BFF всегда его пересылает, парсер пока этот заголовок игнорирует. Повтор ключа — только при ручной отправке. Автоповторов нет. Любой ответ 503 показывает «Не удалось отправить заявку, попробуйте через несколько минут»; если парсер прислал `Retry-After` (секунды или HTTP-date), BFF прокидывает его, и текст становится «попробуйте через ~N мин». Недоступный Redis — 503 `rate_limit_unavailable` и `Retry-After: 30`, на форме это «через ~1 мин». Введённые поля остаются
- Если токен или chat id не заданы, алерт пропускается с записью в лог (сайт не падает)
- `NEXT_PUBLIC_SHOW_FINES=true` — вместе с `approved: true` в `content/fines.ts` показывает таблицу штрафов и калькулятор. Пока юрист не поставил `approved: true`, даже с флагом цифр нет. Без флага блок скрыт целиком.

Токены **не** отдаются в браузер — только серверный BFF.

## Как работают алерты

Когда заданы `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`, BFF пишет менеджеру в Telegram:

1. **Любая проверка URL завершилась** (`phase === done`, с рисками и без) — «Новый клиент с лендинга»:
   - сразу после опроса статуса (`GET /api/checks/{id}`)
   - текст: домен, ссылка, риски да/нет, находки, контакты если есть
   - PDF `sendDocument` только если есть риски и `pdf_ready`
2. **Новая заявка** (`POST /api/leads`) — отдельное сообщение «Новый клиент с лендинга» с полями формы и призывом взять в работу

Без Telegram-переменных сайт работает как обычно, алерты просто не уходят.

## Деплой

В Production env Vercel (`VERCEL_ENV=production`):

- Не задавайте `E2E`, `SUPPRESSION_MOCK`, `OUTBOUND_MOCK`, если `VERCEL_ENV=production` или `PD_DEPLOY_ENV=prod`. Непустое значение останавливает такую сборку. `NODE_ENV` не проверяется: локальная сборка и CI без этих флагов проходят, в том числе при `E2E=1`.
- `ALLOWED_ORIGINS` и `PD_BFF_SIGNING_SECRET` обязательны. Секрет короче 32 байт останавливает такую сборку так же, как тестовая переменная.

На превью эти три переменные можно оставить. В Production их переносить нельзя. На VPS задаётся `PD_DEPLOY_ENV=prod`.

## Parser BFF

Браузер вызывает только:

- `POST /api/checks` `{ "url", "lead?" }` — создать проверку. Если в `lead` есть имя, email или телефон, без `consent: true` BFF отвечает 400 и проверку не создаёт. При согласии парсеру уходит `{ url, mode: "quick" }` и `lead` (`consent: true`, `consent_text_version`, source `landing`). Старый парсер, который отвергает лишние поля, получает повтор с `{ url }`
- `GET /api/checks/[id]` — статус / находки (poll 1,5 с, пока проверка идёт)
- `GET /api/checks/[id]/pdf` — прокси PDF с авторизацией на сервере
- `POST /api/leads` — заявка с обязательным согласием

Если `PARSER_API_BASE` задан, BFF логинится в парсер, создаёт скан и маппит фазы `queued | open | extract | rules | pdf` (+ `done | error | blocked`).

Для **ngrok free** (`*.ngrok-free.dev`) BFF на каждом серверном запросе к парсеру ставит заголовок `ngrok-skip-browser-warning: true` и `User-Agent: PersDannye-BFF/1.0`, чтобы не упираться в interstitial. Токены по-прежнему только на сервере.

## Что есть на сайте

- `/` — лендинг с проверкой URL, FAQ, формой заявки
- `/check` — отдельная страница проверки
- `/privacy`, `/cookies`, `/terms` — юридические страницы
- Cookie-баннер с категориями; аналитика только после согласия
- Согласие на ПДн в форме заявки и в блоке «Контакты для менеджера» (обязательный чекбокс, по умолчанию снят)
- Заявки принимаются только `POST /api/leads`. Страницы и API со списком заявок нет

Реквизиты оператора: `lib/company.ts`.

## CI / npm audit

CI блокирует два аудита.

1. `npm audit --omit=dev --audit-level=high` — зависимости прод-сборки, без исключений.
2. Полный `npm audit --json` разбирает `scripts/audit-allowlist.mjs`. Любой high или critical роняет job.

Единственное исключение — [GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm) (`braces`). Оно действует только если все пути к пакету идут через `eslint-config-next`: это dev-дерево ESLint, опубликованного исправления нет. `eslint-config-next` не понижаем.

Владелец исключения: Сайт 152. Пересмотр 16.11.2026 или раньше, как только выйдет фикс. После `review_by` job падает. Запись: `.github/audit-allowlist.json`.
